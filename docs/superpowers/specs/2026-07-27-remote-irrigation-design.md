# Цифровое поле, итерация 1: водный баланс и удалённое управление поливом

Дата: 2026-07-27

## Цель

Превратить Tomchi из советчика в исполнителя. Фермер должен уметь запустить полив
по рассчитанной норме, не выходя в поле — что критично в летнюю жару, когда выход
на участок опасен для здоровья, — и наблюдать за ходом полива из приложения.

Эта итерация реализует всё, что не требует физического железа: научный расчёт
влаги в почве, модель устройства, облачное состояние сеанса полива, пульт
управления и завершение сеанса на сервере. Реальный контроллер, датчики и камеры
подключаются в следующих итерациях без переписывания интерфейса.

## Границы

**Входит:** водный баланс FAO-56, виртуальное устройство, запуск и остановка
полива, живой прогресс, история сеансов, завершение сеанса планировщиком,
уведомление в Telegram, баннер опасной жары.

**Не входит:** реальное железо и протоколы к нему, камеры и видеопоток,
автоматические правила полива без участия человека, подписка и тарификация,
мультизонный полив (несколько клапанов на одно поле).

## 1. Научное ядро: водный баланс

Без физического датчика запас влаги в корневом слое вычисляется по водному
балансу FAO-56. Это стандартная методика, а не имитация: тот же расчёт применяют
профессиональные системы орошения.

### Формулы

```
Zr   = глубина корней на текущий день сезона, м
TAW  = AW_почвы (мм/м) × Zr                     полная доступная влага, мм
p_adj = clamp(p + 0.04 × (5 − ETc), 0.1, 0.8)   поправка по ETc текущего дня, мм/сут
RAW  = p_adj × TAW                              легкодоступная влага, мм
Dr   = дефицит влаги в корневом слое, мм        0 = полная влагоёмкость
```

Дефицит накапливается день за днём от последнего события в журнале поля:

```
Dr(день) = clamp(Dr(вчера) + ETc(день) − осадки(день), 0, TAW)
```

Производные величины:

```
влажность, %      = 100 × (1 − Dr / TAW)
нужен полив       = Dr ≥ RAW
норма нетто, мм   = Dr                          долив до полной влагоёмкости
норма брутто, м³  = Dr / КПД_метода × 10 × площадь_га
дней до полива    = проекция Dr вперёд до пересечения RAW
```

Проекция вперёд использует ET0 из кэша прогноза Open-Meteo на те дни, что в нём
есть, и климатическую норму региона на остальные; будущие осадки берутся из
прогноза. Если пересечение не наступает за 30 дней, возвращается `null`.

### Новые константы

Таблицы ниже живут в `engine/soilWater.ts` (свойства почвы) и `data/crops.ts`
(свойства культур), рядом с уже существующими данными того же рода.

Доступная влага почвы, мм на метр корневого слоя (FAO-56, таблица 19, средние
значения диапазона):

| Песчаная  | 80       |

| Глинистая | 150      |

Глубина корней и доля допустимого истощения по культурам (FAO-56, таблица 22;
для орошаемых условий взят нижний край диапазона Zr, как предписывает FAO-56):

| Культура   | Zr нач., м | Zr макс., м | p    |
|------------|------------|-------------|------|
| Хлопчатник | 0.30       | 1.00        | 0.65 |
| Пшеница    | 0.30       | 1.50        | 0.55 |
| Томаты     | 0.25       | 0.80        | 0.40 |
| Виноград   | 0.40       | 1.20        | 0.35 |
| Яблоня     | 0.40       | 1.20        | 0.50 |
| Дыни       | 0.30       | 0.90        | 0.45 |
| Картофель  | 0.25       | 0.50        | 0.35 |

Корни растут линейно от `Zr нач.` в день посева до `Zr макс.` к началу фазы
цветения (`mid`), далее остаются постоянными.

### Источники входных данных

Все уже есть в проекте:

- **ETc** — `et0At()` из `engine/irrigation.ts` (климат региона) и `stageAt()` для Kc.
  Если в кэше есть прогноз Open-Meteo на нужную дату, берётся его фактический
  ET0 как более точный.
- **События полива и дождя** — `field.log` (`WateringEvent`).
- **Тип почвы, культура, площадь, метод** — `FieldConfig`.

### Принятые упрощения

`weather.ts` запрашивает только прогноз вперёд (`forecast_days=7`), исторических
осадков нет. Поэтому прошедший дождь учитывается по журналу: событие типа `rain`
обнуляет дефицит так же, как полив. Это соответствует текущему поведению
приложения, где `lastEventDate()` уже считает дождь и полив равнозначными.

Слабое место: слабый дождь в реальности не восполняет влагоёмкость полностью.
Путь улучшения — запрашивать `past_days` у Open-Meteo и учитывать фактические
миллиметры, либо получать их с реальной метеостанции. В спеке зафиксировано как
известное ограничение, не как дефект.

Дренаж ниже корневого слоя и капиллярный подъём не моделируются: дефицит
ограничен снизу нулём, что эквивалентно допущению «избыток воды уходит».

### Файл

`src/engine/soilWater.ts` — только чистые функции, без обращений к сети и
хранилищу. Работает офлайн.

```ts
export interface SoilWater {
```

## 2. Модель данных

Миграция `supabase/migrations/0004_devices.sql`. Стиль и политики RLS повторяют
существующие таблицы: владелец видит только свои строки, бот работает через
service role в обход RLS.

```sql
create table if not exists public.devices (
  id uuid primary key default gen_random_uuid(),
  owner uuid not null default auth.uid() references auth.users (id) on delete cascade,
  client_field_id text not null,
  kind text not null default 'virtual',
  flow_lpm numeric not null,
  status text not null default 'online',
  last_seen timestamptz,
  created_at timestamptz not null default now(),
  unique (owner, client_field_id)
);

create table if not exists public.irrigation_sessions (
  id uuid primary key default gen_random_uuid(),
  owner uuid not null default auth.uid() references auth.users (id) on delete cascade,
  device_id uuid not null references public.devices (id) on delete cascade,
  client_field_id text not null,
  started_at timestamptz not null default now(),
  planned_end_at timestamptz not null,
  planned_liters numeric not null,
  ended_at timestamptz,
  delivered_liters numeric,
  status text not null default 'running'
    check (status in ('running', 'done', 'stopped', 'failed')),
  source text not null default 'manual'
    check (source in ('manual', 'auto', 'bot')),
  notified boolean not null default false
);
```

Индексы: `devices (owner)`, `irrigation_sessions (owner, client_field_id)` и
частичный `irrigation_sessions (planned_end_at) where status = 'running'` — по
нему работает планировщик.

Ключевое решение: **сеанс описан метками времени, а не тикающим таймером.**
Прогресс вычисляется из `started_at` и `planned_end_at` при каждом чтении.
Поэтому полив продолжается, когда приложение закрыто, телефон выключен или
фермер открыл другое устройство. Так же ведёт себя настоящий контроллер.

Одно устройство на поле — ограничение `unique (owner, client_field_id)`.

Два элемента схемы заведомо не используются в этой итерации и оставлены как
точки расширения под реальное железо: `devices.status` и `devices.last_seen`
(виртуальное устройство всегда на связи, реальное — нет) и значения `auto` и
`bot` в `irrigation_sessions.source`. Добавить их сразу дешевле, чем менять
ограничение `check` и типы позже.

## 3. Слой драйвера

`src/lib/devices.ts` — единственная точка, через которую UI общается с
устройством. Сегодня внутри — записи в Supabase. Когда появится реальный
контроллер, меняется только реализация этих функций; компоненты не трогаются.

```ts
export interface Device {
  id: string;
  fieldId: string;
  kind: 'virtual';
  flowLpm: number;
  status: 'online' | 'offline';
}

export interface Session {
  id: string;
  startedAt: string;
  plannedEndAt: string;
  plannedLiters: number;
  status: 'running' | 'done' | 'stopped' | 'failed';
  source: 'manual' | 'auto' | 'bot';
  endedAt?: string;
  deliveredLiters?: number;
}

export interface SessionProgress {
  session: Session;
  fraction: number;       // 0..1
  deliveredLiters: number;
  minutesLeft: number;
}

connectDevice(fieldId: string, flowLpm: number): Promise<Device | null>
getDevice(fieldId: string): Promise<Device | null>
updateDevice(fieldId: string, patch: { flowLpm?: number }): Promise<void>
startIrrigation(fieldId: string, liters: number): Promise<Session | null>
stopIrrigation(sessionId: string): Promise<void>
getActiveSession(fieldId: string): Promise<SessionProgress | null>
listSessions(fieldId: string, limit?: number): Promise<Session[]>
```

Как и `lib/sync.ts`, функции не бросают исключения: при отсутствии облака или
сетевой ошибке возвращают `null` либо пустой список, а вызывающий код показывает
понятное сообщение.

Прогресс считается на клиенте чистой функцией — её же использует планировщик:

```
elapsed  = now − startedAt
fraction = clamp(elapsed / (plannedEndAt − startedAt), 0, 1)
delivered = flowLpm × elapsed_в_минутах, но не больше plannedLiters
```

### Расход воды

Длительность сеанса выводится из расхода: `минуты = литры / flow_lpm`.

При подключении устройства поле расхода предзаполняется оценкой по методу полива
и площади, фермер может исправить:

| Метод      | Оценка, л/мин на гектар |
|------------|-------------------------|
| По бороздам| 500                     |
| Дождевание | 250                     |
| Капельное  | 135                     |

### Правила безопасности

Система открывает клапан, поэтому ограничения обязательны:

- Длительность сеанса ограничена 8 часами. Если расчёт даёт больше, полив
  запускается на 8 часов, а фермеру показывается предупреждение, что норма не
  будет вылита за один сеанс.
- Нельзя запустить второй сеанс, пока активен первый — проверка перед вставкой
  и отображение активного сеанса вместо кнопки запуска.
- Перед запуском — подтверждение с указанием объёма и времени.
- Кнопка остановки доступна всегда, пока сеанс активен.

## 4. Планировщик завершения

`netlify/functions/irrigation-tick.mts`, по расписанию каждые 5 минут. Работает
через service role, поэтому видит сеансы всех владельцев.

Алгоритм:

1. Выбрать сеансы со `status = 'running'` и `planned_end_at <= now()`.
2. Проставить `status = 'done'`, `ended_at = planned_end_at`,
   `delivered_liters = planned_liters`.
3. Вставить запись в `watering_events` с типом `watered` и временем начала
   сеанса. Благодаря этому журнал, календарь, «Эффект» и дата следующего полива
   обновляются существующим кодом, без дублирования логики.
4. Если у владельца есть связанный чат в `bot_links` и `notified = false` —
   отправить в Telegram «Полив завершён, вылито N м³» и выставить `notified`.

Шаги 2–4 идемпотентны: повторный запуск на уже закрытом сеансе ничего не меняет,
так как выборка идёт только по `status = 'running'`, а флаг `notified`
предотвращает повторное уведомление.

Остановка вручную (`stopIrrigation`) выполняет те же шаги 2–3 немедленно, но со
`status = 'stopped'` и фактическим объёмом на момент остановки. Запись в журнал
создаётся, только если вылито не меньше 20% плановой нормы — иначе случайное
касание кнопки исказит статистику расхода воды.

## 5. Интерфейс

### Новая вкладка «Полив»

Пятая вкладка в нижней панели, иконка `tap` (кран) — уже есть в `Icon.tsx`.
Ключи локализации: `tabControl` (uz `Sug'orish`, ru `Полив`).

Четыре состояния экрана:

**Облако не настроено.** Показывается «бак влаги» и рекомендация по норме, ниже —
пояснение, что удалённое управление требует подключения к облаку. Нерабочих
кнопок нет.

**Устройства нет.** Экран подключения (`ConnectDevice.tsx`): список типов
устройств — контроллер клапана, датчик влажности, метеостанция, камера — все с
пометкой «скоро», и отдельная кнопка «Попробовать в демо-режиме», создающая
виртуальное устройство. Это честно показывает и текущее состояние, и роадмап.

**Устройство есть, полив не идёт.** «Бак влаги», рекомендуемая норма в м³ и
оценка длительности, кнопка «Полить сейчас» с подтверждением, расход воды с
возможностью правки, история сеансов.

**Полив идёт.** Живой прогресс (доля, вылито литров, осталось минут),
обновление раз в секунду от локального времени без обращений к сети, кнопка
«Остановить». Постоянная плашка «виртуальное устройство».

### Бак влаги

`MoistureGauge.tsx` — вертикальная шкала: заполненная часть равна
`100 − 100 × Dr/TAW`, отметка порога `RAW` показывает, где начинается зона
стресса. Цвет: выше порога — `leaf`, ниже — `clay`. Подпись цифрой в процентах.

Компонент используется в двух местах: полноразмерный на вкладке «Полив» и
компактный на «Сегодня», чтобы фермер видел влажность без перехода.

### Баннер опасной жары

`weather.ts` уже отдаёт `tMax`. Когда прогноз на сегодня даёт `tMax ≥ 40`, наверху
вкладки появляется предупреждение: «Опасная жара — не выходите в поле. Запустите
полив отсюда». Это связывает существующие погодные алерты с новым пультом и
реализует основной сценарий, ради которого делается итерация.

Порог 40 °C вынесен в константу `DANGEROUS_HEAT_C` рядом с `RAIN_SKIP_MM`.
В черновике спеки стояло 38 °C; при сборке взяли 40 °C, и это подтверждено —
на юге Узбекистана 38 °C летом рядовая температура, и баннер при таком пороге
горел бы неделями подряд, а предупреждение, которое видно всегда, не читают.

## 6. Поведение без облака

Водный баланс, «бак влаги» и расчёт нормы — чистая математика на устройстве,
работают всегда, в том числе офлайн.

Удалённое управление принципиально требует сервера: команда должна дойти до поля,
даже когда телефон выключен. Поэтому при `supabaseEnabled === false` пульт
показывает объяснение вместо кнопок. Это ограничение архитектуры, а не заглушка.

## 7. Тестирование

В проекте нет тестового окружения. Для этой итерации добавляется `vitest`
(dev-зависимость, скрипт `npm test`) и покрывается только `engine/soilWater.ts` —
чистая математика, ошибки в которой не видны глазом, но приводят к неверной
норме полива.

Проверяются:

- TAW и RAW для каждого типа почвы и каждой культуры на известных значениях;
- рост глубины корней: начало сезона, середина, после фазы цветения;
- накопление дефицита за N дней без осадков и его сброс событием полива;
- ограничение дефицита сверху величиной TAW и снизу нулём;
- поправка `p_adj` на границах диапазона;
- вне сезона возвращается `inSeason: false` без деления на ноль.

Логика прогресса сеанса (чистая функция расчёта доли и объёма) покрывается тем же
набором: начало, середина, конец, время после планового окончания.

Остальные слои проверяются вручную в браузере: подключение устройства, запуск,
прогресс, остановка, появление записи в журнале.
